### Q5 调用模型时「余额不足」「Key 失效」分别返回什么错误？

**已核实（本仓库，来自 PT 官方口径 A.04 与真机记录）**

  |---|---|---|
  | `401 Unauthorized` | Key 失效 / 过期 / 缺失 | Key 错误或未传 |
  | `402 Payment Required` | 余额不足 / 额度耗尽 | 生成时点数用尽 |

- 模型下架真实报文（A.21）：`403` + `model_not_found ... not listed (pending), please contact admin to enable it`，且该模型**仍在 `/v1/models` 列表里**。
- 只读账户命令（balance/usage/logs/agreement）不会返回 402。

**需要 PT 确认**（重点是「精确报文」而非状态码大类，errors 字典每类要一条真实样例）
1. 以下 6 种场景的**精确 HTTP 状态 + 错误码字符串 + message 文本**（请给脱敏原文）：
   - 账号余额不足 / 额度用完 / Key 停用 / Key 过期 / Key 无该模型权限 / 内容被安全策略拦截
2. 403 的语义是否仍可能重载？「余额不足」在新版是否**统一为 402**？历史 403 报文是否还会出现？
3. `429` 限流是否返回 `Retry-After` 头？限流是按 Key、按账号还是按模型？
4. 上游 5xx / 超时，PT 侧返回的状态码与错误体是什么？
5. 参数不支持（如某模型不支持 tools / 图片 / `response_format`）与输入超长（`context_too_long`）分别返回什么？

**为什么需要**：需求 4 的错误码字典共 9 类（`rate_limited` / `upstream_error` / `timeout` / `auth_invalid` / `insufficient_balance` / `model_unavailable` / `param_unsupported` / `content_filtered` / `context_too_long`），每类要一条真实样例决定 Agent 是「重试 / 换模型 / 停止 / 压缩上下文」。

## 3. 新增事实资料（以后查这里）

### 3.1 生成域 HTTP 状态码语义（最新口径）

| HTTP | 需要区分的含义 |
|---|---|
| `400` / `413` / `415` / `422` | 参数错误 / 输入过大 / 格式不支持 / 语义或组合不支持 |
| `401` | 凭据无效 |
| `402` | 余额不足 |
| `403` | 权限不足**或**模型已下架 —— **需要能区分这两种原因** |
| `404` / `409` / `410` | 资源不存在 / 幂等冲突或状态冲突 / 已过期（**跨账号访问可统一返回 404 防止枚举**） |
| `429` / `503` / `5xx` | 限流 / 容量暂不可用 / 上游异常 —— **需标明该请求是否可能已被受理，并附信号**（见 §2 Q8） |

> `429` **按账户**维度限流（不是按 Key / 按模型）。
> 附件 B §「公共状态码」另列 `400`（参数缺失/格式不合法）、`404`（套餐下架/模型未接入）、
> `409`（状态冲突，如存在未支付订单）、`422`（参数语义校验失败，如低于起充额）、`500`。
> 两处 `code` 与 HTTP 状态码**并行使用，业务判断以响应体 `code` 为准**（附件 A/B 共同说明）。

### 3.2 生成域错误分类（含 error.code）

| 语义 | 状态码 | 语义分类 |
|---|---|---|
| 余额不足 / 额度耗尽 | `402 Payment Required` | 客户端应**充值后再试** |
| Key 停用 / Key 过期 | `401 Unauthorized` | Key 自身不可用 —— `token_invalid` / `expired` / `disabled` |
| Key 无该模型权限 | `403 Forbidden` | Key 可用但**无权调用此模型** |

> 与仓库 `README.md` / `README.zh-CN.md` §17.1（`README.zh-CN.md:493-505`）现有 401/402/403 表**一致**，
> 本批只是把 401 拆细到停用/过期、把 403 收敛为「无该模型权限」，并补上 error.code 串。
> **403「权限不足 vs 模型已下架」的区分方式仍未给**（PT 被要求能区分）→ R2。

## 8.4 ⚠️ 新暴露的口径张力：流中途 settle vs 全额 Refund（R10）

**两条证据**：

1. **第三批 Q8**（§7.1 第 1 行）：「Submit 成功但生成失败 → 已预扣 → polling 检测 `FAILURE` → **同循环内全额 `RefundTaskQuota`**」，
   并据此在 §7.1 把 `charging.charged_on_failure` / `charged_on_timeout` 都定为 **`false`**。
2. **第四批矩阵**（§8.1 #5–7）：「流中途 scanner 错误 / streaming timeout / 客户端主动断 → **不会触发 controller 层 Refund；
   但 `adaptor.DoResponse` 内部已做 settle**」。

**为什么不能直接互相套用**：

- 第三批的措辞是 `Submit` / `polling` / `FAILURE` / `RefundTaskQuota` —— 典型的**异步任务（视频 Submit / Polling）链路**。
- 第四批 #5–7 的措辞是 `SSE` / `finish_reason` / `adaptor.DoResponse` —— 典型的**chat 流式链路**。
- 矩阵里把两者分开列（#1–7 是 chat，#8–9 是异步 Submit），**正好支持「两条链路、两套结算」的解读**。

**推断（需 PT 确认，不写进 catalog）**：

| 链路 | 失败时 | 推测扣费 | 对 `charging` 的影响 |
|---|---|---|---|
| 异步视频任务 | `FAILURE` / 超时 | 全额 Refund → `false` | 维持 §7.1 口径 |
| chat 首包前 | 5xx / 超时 | 自动 Refund → `false` | 维持 |
| **chat 流中途** | 已产出部分内容后 error / timeout / abort | **内部已 settle，可能按已产出 token 计费 → 未必 `false`** | **`charged_on_failure` 需按链路分叉，或改用 `charging.notes` 写明例外** |

> **R10 要问的一句话**：流中途失败（含客户端主动断）是否产生实际扣费？若产生，按什么计量（已产出 token / 预扣全额 / 固定）？
> 消费记录里这类请求的 `status` 与 `quota` 长什么样？
> **不答的后果**：Agent 把「HTTP 200 + `finish_reason=error`」当成功或盲目重试，都可能造成对账差异。

## 9.1 第五批原始输入固化

### 9.1.1 8 行对比表（原样）

| 场景 | 网关本地拦截？ | HTTP 状态码 | `error.code` | `error.type` |
|---|---|---|---|---|
| 模型不支持 tools | ❌ 透传 | 上游返回（通常 400） | 上游原 code（如 `unsupported_parameter`） | 上游原 type（如 `invalid_request_error`） |
| 模型不支持 vision / `image_url` | ❌ 透传 | 上游返回（通常 400） | 上游原 code | 上游原 type |
| 模型不支持 `response_format` | ❌ 透传 | 上游返回（通常 400） | 上游原 code | 上游原 type |
| `context_too_long` | ❌ 透传 | 上游返回（通常 400） | 上游原 code（如 `context_length_exceeded`） | 上游原 type |
| `model` 字段为空 | ✅ 本地拦截 | 400 | `invalid_request` | `api_error` |
| `max_tokens` 超 Int32 | ✅ 本地拦截 | 400 | `invalid_request` | `api_error` |
| 上游返回非 JSON body | ✅ 网关兜底 | 上游状态码 | `bad_response_status_code` | `api_error` |
| 模型不在上架列表 | ✅ 中间件拦截 | 400 | `invalid_request` | `upstream_error` (middleware abort) |

**归三类**：① **上游参数类**（4 行）PT 网关不拦截、原样透传；② **本地前置校验**（2 行）`invalid_request` / `api_error`；
③ **网关兜底 + 中间件**（2 行）`bad_response_status_code` / `upstream_error`。

### 9.1.2 返回体形态与真机报文

> 「与『参数不支持』完全相同：上游 error code 和 message **原样保留**，网关仅在 message 末尾追加 `request_id`。」

```http
HTTP 400 Bad Request
{
    "error": {
        "message": "Maximum context length for gpt-4o is 128000 tokens. (request id: xxx)",
        "type": "invalid_request_error",
        "param": "messages",
        "code": "context_length_exceeded"
    }
}
```

> 这条同时给出三件以前没有的东西：`context_too_long` 的精确 `code` / `type` / `param`、

## 9.6 Seedance 签协议：本仓库如何处理（已完整实现，四层）

| 层 | 实现 | 位置 |
