4. ⚠️ 本批最重要的发现：两批答复之间的口径张力（R10）

这是我方交叉核对发现的，PT 没有主动点明

第三批 Q8

「Submit 成功但生成失败 → 已预扣 → polling 检测 FAILURE → 同循环内全额 RefundTaskQuota」
据此 §7.1 把 charging.charged_on_failure / charged_on_timeout 都定成 false。

第四批矩阵 #5–7

「流中途失败 → 不会触发 controller 层 Refund；但 adaptor.DoResponse 内部已做 settle」
HTTP 200 已锁死，普通重试逻辑根本识别不到失败。
推断（需 PT 确认，不写进 catalog）：前者措辞是 Submit / polling / FAILURE / RefundTaskQuota → 异步视频链路； 后者是 SSE / finish_reason / adaptor.DoResponse → chat 流式链路。两条链路两套结算就能自洽。 但若如此，流中途失败可能按已产出 token 计费，charging.charged_on_failure 就不能一律 false，需按链路分叉或写明例外。
要问 PT 的一句话：流中途失败（含客户端主动断）是否产生实际扣费？按什么计量？消费记录里这类请求的 status / quota 长什么样？
