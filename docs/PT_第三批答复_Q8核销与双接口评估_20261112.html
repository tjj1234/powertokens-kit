1. Q8 失败扣费与幂等 · 逐条核销

PT 给的 7 行答复，逐条对应清单 §B 组 Q8 的原三问
汇总问题PT 答案解读
Submit 成功但生成失败已预扣 → polling 检测 FAILURE → 同循环内全额 RefundTaskQuota最终不扣费
轮询超时已预扣 → sweepTimedOutTasks（默认 24h）→ 标 FAILURE + 自动退款（legacy 任务除外）最终不扣费
退费到账时间零延迟，DB 事务级同步退回（钱包 / 订阅 / Token 额度 / 专属积分同时退）无需轮询

会不会二次扣费？不会。CAS 保证终态只结算一次；refund 后 Quota 置 0，二次 RefundTaskQuota 直接早退无重复扣费
原三问全部有答案：① 失败 / 超时 / 结果未知最终都不扣费，失败即时退、超时最长 24h 退、到账零延迟； ② 幂等靠服务端 CAS + Quota=0，不靠客户端幂等键（Q2 client_operation_id 作废不构成缺口）； ③ task_id 复查完全安全。Q8 🔴 → 🟢，R5 从待确认清单划掉。
注意措辞：「不扣费」指最终结算，不是「没有预扣」——PT 明确 Submit 成功即已预扣。 Agent 若在任务进行中展示余额会看到暂时减少，这不是错误扣费，也不应触发重试。
对现有代码是正向印证：pt_video.py:733/748 轮询超时后提示「稍后可单独 GET /v1/videos/{task_id} 复查」，PT 答案证实该提示安全 → 可从经验做法升级为 verified 口径， 代码无需改动。

⚠️ 三处术语撞车，别误判成「已覆盖」
  • ① 「透传」5 处（catalog:1127/1133/1154/1160/1960）全是 chat thinking_param 的参数透传（mimo 系），不是接口变体。
  • ② README:354/511「约 24 小时」是 image data[].url 临时签名地址；且「URL 过期」≠「文件本体 24h 后删除」。
  • ③ vendor_endpoint 86/86 都有，但语义不统一（seedance 填统一端点、其余填厂商原生路径），代码从不读它做路由。有字段 ≠ 覆盖概念 —— 反而是「已存了一部分透传端点路径却没升级为契约」，seedance 这族全空着。
「文件永久保存」≠「下载 URL 永久」：对象存储里文件本体可长期留存，签名链接仍可能 24h 过期、需重新签发。 所以 S2 有答案前，无论走哪条路径，成功即下载/转存都仍是必须的 —— 本仓库默认行为已经做到。
