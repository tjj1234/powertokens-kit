### 2.1 Q1–Q8 · 最初的 8 个问题

#### Q1 · 有没有「用 API Key 查 key_id」或「列出我的 Key」的接口？

- **原始提问**：是否存在独立的 Key 查询/列表接口？`key_id` 是否等于 `/v1/billing/balance` 返回的 `key_id`？个人访问令牌里能否解析出 `key_id`？账户域 host 与鉴权头是否仍为裸 Key？
- **PT 答复**：第 2 批口述 —— 「**没有独立查询 key 的接口**，目前所有的接口就是给你 2 份文档，以及 PT 线上文档」；「**不可以，个人令牌是账号层级的，账户下面包含多个 key**」；「没明白…如果都是 key id 就是同一个」。D4 §5 定稿：`key_id` = **数字**，tokens 表主键；`key_masked` = **脱敏串**，只做展示；调用方只提供数字 `key_id` 即可；`/key/info` 返回数字 `key_id` + `key_masked`。
- **影响到的功能**：① 后置账户客户端（`key_id` 必填，不能自动发现，必须由调用方传入）；② `logs` 的 `key_id` 过滤（历史实现按脱敏串匹配，PT 承认是遗留，将统一）；③ 用量面板按 Key 拆分对账；④ `catalog` 的账户相关字段（本次范围已收窄，只保留 `request_id` 位置一条）。
- **最终处置**：✅ 闭环。不做 Key 列表接口；不做 AK/SK 双头（C2）；账户客户端按 B4/B5 **后置**，本轮不建。
- **对应文档**：清单 §2 Q1 / §3.6；SSOT §2.8；`PT_API_2.0.0_官方答复核销_20261112.md`；`PT_账户接口_默认模块依据_20261112.md`。

#### Q2 · `client_operation_id` 怎么传？

- **原始提问**：字段拼写与位置（header / body / query）？是不是幂等键？重复提交返回同一 `task_id` 吗？适用范围？与 `request_id` 什么关系？
- **PT 答复**：第 1、2 批**两次确认**「**没有这个 id**」。它只出现在 D2 旧规划稿（2.0.0 支付分册）的过滤参数里，属规划残留。
- **影响到的功能**：`charging` / `submission` 的 `idempotency_key_supported`、`idempotency_header`、`duplicate_returns_same_task` 三个字段；重复提交防扣费策略。
- **最终处置**：⚫ **作废闭环**。三个幂等字段继续 `null`；不生成、不透传该字段；不再向 PT 追问。幂等改由**服务端**保障（Q8 / D4 §10：三重防二次退费）。
- **对应文档**：清单 §2 Q2；SSOT §4.1；`PT_最终待确认清单_可直接发给PT.md`「已确认无需再答」。

#### Q3 · 调用模型的响应里怎么拿 `request_id`？

- **原始提问**：header 还是 body？确切字段名？chat / video / image / audio 四类都有吗？异步是提交时返回还是轮询里返回？流式在第几个 chunk？失败请求有没有？
- **PT 答复**：第 2 批口述 —— 「**request_id 在 body 里面，你可以测试下**」「**都有，异步视频是提交时返回**」「流式响应下 **request_id 只在 header**」「4xx/5xx 也返回，而且有两层保障：**header 一定有，body 的 `error.message` 里也有**」。第 5 批补精确埋点格式：末尾追加 `(request id: xxx)`。D4 §3 补：`X-Oneapi-Request-Id` **只用于报障定位，不是受理信号**。
- **影响到的功能**：① 管理员用量面板把「一次对话」对应到「一条消费记录」；② 报障定位；③ `retry_policy.request_id_observed`（真机回写）；④ `catalog` 里唯一保留的账户相关字段。
- **最终处置**：✅ **实质闭环（真机 T3）**。成功响应 body 字段名 = **`id`**（48 位十六进制），与 `X-Request-Id` header 同值；另有 `X-Oneapi-Request-Id`（报障）、`X-Client-Request-Id`（调用方自定义）；流式 header 只回 `X-Oneapi-Request-Id`，但 SSE chunk 内仍带 `id`；失败时 `error.message` 末尾 `(request id: xxx)` 与 header 同值（T4 双证）。**异步视频提交响应字段名仍未实测**（余额不足未提交）。
- **对应文档**：清单 §2 Q3 / §3.5 / §9.2.2；SSOT §2.7 / §10.2.3；`catalog.json → retry_policy.request_id_observed`。

#### Q4 · `/v1/logs/list` 是否已上线？GET 还是 POST？`limit` 默认值和上限？

|---|---|---|---|---|
| 模型未上架 / 已下架 / 从未接入 | 403 | `model_not_found` | `api_error` | 换模型或提上架需求 |
| Key 无权访问该模型 | 403 | `token_model_forbidden` | `api_error` | 换 Key / 加模型授权 |
| Key 无权访问该分组 | 403 | `token_group_forbidden` | `api_error` | 换分组 |
| 指定渠道已被禁用 | 403 | `channel_disabled` | `api_error` | 去掉渠道指定 |
| 已上架、但当前分组无可用渠道 | **503** | `model_not_found` | `api_error` | 找运营（**同 code，靠 503 区分**） |
| 请求体非法 / 未指定 model | 400 | `invalid_request` | `api_error` | 改请求 |
| 上游原始 400 | 400 | 上游 code（多为 `invalid_request`） | `upstream_error` 或上游 type | 改请求，**不重试** |

**受理 / 重试 4+1 规则**：非 2xx → 没受理、已退费、✅ 可重试；`200 + JSON` → 已结算、❌；`200 + SSE` 正常末帧 → ❌；`200 + SSE` `error/timeout/abort` → **已扣费**、❌（会二次扣费）；异步 `200 + task_id` → 已受理、查状态不要重复提交。
**429**：`model_rate_limited` + `Retry-After` 一定有（网关默认 5s），网关限流在预扣费之前不产生费用，属「肯定没受理」可安全重试。
