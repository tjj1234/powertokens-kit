# Seedance 双接口与产物有效期 · 覆盖评估

> 版本：2026-11-12 · 对象：`tjj1234/powertokens-kit` → `powertokens-video/pt-gateway`
> 触发：用户补充 PT 事实「类似 seedance 这种有两个接口，一个是标准接口，一个是透传接口；标准接口的字段没有透传接口的字段全；标准接口生成的文件是永久保存，透传接口生成的是 24 小时有效」，并附 README §4「能力总览」截图，问「你看下是否覆盖了这块」「这个是否也要适配呢」。
> 性质：**只读评估，未改任何代码 / catalog / README**。同一批事实已沉淀到 `docs/PT_待确认问题清单_20261112.md` §7。

## 0. 结论先行

1. **没覆盖。** catalog 数据、生成代码、README 文档三层都没有「标准接口 / 透传接口」这个概念，也没有任何产物有效期字段。截图里的 §4 表格只有 `image / video / seedance` 三类型、生成机制、素材格式——**没有接口变体，也没有 TTL**。
2. **但有三处很容易误判成「已覆盖」的撞车**，见 §2.2：尤其 catalog 里那 5 处「透传」其实是 chat 的参数透传，README 里那两处「24 小时」是 image 的签名 URL。
3. **要不要适配，取决于你是否要用透传接口。**
   - 当前网关只走 `/v1/videos` 标准端点，按 PT 说法**产物永久保存**，反而是更省事的一条路。
   - 建议：**补 catalog 数据 + 文档（纯加字段、零风险），暂不改生成代码**。
   - 只有当业务确实需要标准接口没有的字段（`negative_prompt` / `seed` / `ratio` / 多模态参考 / `content` 原样透传等）时，才值得上 P1 代码改造，并同时承担 24h 内转存的新义务。
4. **生成链路本轮一行都不用改**——与上一批 PT 答复第 4 条「正常调用模型生成都不用改，都是正常的」一致。

### 2.2 ⚠️ 三处术语撞车（别误判成「已覆盖」）

| # | 表面证据 | 实际含义 | 为什么不算覆盖 |
|---|---|---|---|
| 1 | `catalog.json` 有 5 处「透传」（:1127 / :1133 / :1154 / :1160 / :1960） | 全是 **chat 模型 `thinking_param`** 的「参数透传」标注（mimo 系），以及 `multimodal_source` 里「网关对多模态原样透传」 | 说的是**请求参数原样上送**，不是**接口变体** |
| 2 | `README.md:354/511`、`README.zh-CN.md:354/511` 写「`data[].url` 临时签名地址（约 24 小时）」 | **image 文生图**返回 URL 的签名有效期 | 既不是视频产物，也不是透传接口；且属于「**URL** 过期」，与「**文件本体** 24h 后删除」不同 |
| 3 | `catalog.json` 86/86 模型都有 `vendor_endpoint` | 语义不统一：7 个 seedance 全填 `/v1/videos`（PT 统一端点），其余填厂商原生路径如 `/ali/api/v1/services/aigc/...`、`/vidu/ent/v2/img2video`、`/minimax/v2/video_generation` | **有字段 ≠ 覆盖概念**：没有标注哪个是透传端点，代码也从不读它做路由（`pt_gateway.py` 只用 `kinds[].submit`） |

> 第 3 点最值得注意：catalog 其实**已经存了一部分透传端点路径**（Vidu / MiniMax / Ali），只是当初当作「上游厂商提示」记录，没有升级为可调用的契约；seedance 这一族反而全都空着。

## 3. 两张接口的对照（已知 / 待确认）

| 维度 | 标准接口 | 透传接口 |
|---|---|---|
| 端点 | `POST /v1/videos` + `GET /v1/videos/{task_id}`（本仓库当前唯一路径） | 供应商原生端点，PT CLI 按模型名自动分派；字节 `/byteplus/api/v3/...` 等**只有前缀** |
| 请求体 | PT 归一化字段：`model` / `prompt` 或 `media[].text` / `size` / `ratio` / `seconds`（字符串）/ `generate_audio` / `media[]` | 上游原生字段，可用 `--params` 合并；「完全透传」时 `content` / `media` 数组原样发，只补 `model` |
| 字段完整度 | **较少**（用户原话） | **更全**（`negative_prompt` / `seed` / `ratio` / `watermark` / `callback_url` / 多模态参考等） |
| 产物保存 | **永久保存**（用户原话） | **24 小时有效**（用户原话） |
| 签协议 / `asset://` | 需签《Asset Library User Agreement》；图生视频素材强制 `asset://`（本仓库已实现） | **未知** → S3 |
| 下载 URL | 未知是否永久 → S2 | 上游签名 URL 24h（F5 旁证） |
| 本仓库支持 | ✅ 已实现 | ❌ 未实现 |

> **「文件永久保存」≠「下载 URL 永久」。** 这两件事在对象存储里通常是分开的：文件本体可以长期留存，
> 而对外签名链接仍可能 24h 过期、需要重新签发。所以在 S2 有答案之前，**无论走哪条路径，
> 成功即下载 / 转存都仍是必须的**——这正是本仓库默认行为已在做的事（§2.1 最后一行）。

## 4. 影响分析：这个差异到底会不会咬到我们

| 场景 | 当前行为 | 风险 |
|---|---|---|
| 只用标准接口生成 + 默认下载 | 拿 `metadata.url` → 落盘本地 | 🟢 无。产物永久 + 已转存，双保险 |
| 只用标准接口 + `--no-download` 只存 URL | 只拿 URL | 🟡 若签名 URL 也会过期（S2 未定），隔天可能 404 |
| Agent 读 catalog 选接口 | catalog 只写了一条 `/v1/videos` | 🟡 **不会选错，但会「不知道还有一条路」**：需要全字段时无从判断，可能误以为 PT 不支持 |
| 将来接透传接口 | 无 TTL 处理 | 🔴 24h 后产物丢失；需在成功回调内强制转存，并给 Agent 显式 `ttl` 提示 |
| 现有 README §4 表格 | 只列三类型 + 生成机制 | 🟡 读者（含 Agent）会以为 Seedance 只有一种调用方式 |
